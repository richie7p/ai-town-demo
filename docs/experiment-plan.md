# 從 demo 到正式實驗

本次完成研究引擎與視覺展示的工程起點。不要把 `npm run simulate` 產生的規則型資料計為校準、先導或正式 LLM 場次。

| 階段 | 場數 | 接下來要完成的事 | 啟動下一階段的依據 |
| --- | ---: | --- | --- |
| 工程 demo | 不列研究樣本 | 時序、設備、合作、記憶可見性、人工指標與重播 | 本版測試與介面檢查；正式新增規則仍須補測 |
| 模型接入 | 短流程 | 安全的伺服器端 API、結構化提議、日終反思、實際 tokens／費用、服務重試與檢查點 | 兩角色流程，再擴到八角色；模型規格與價格重新查核 |
| 校準 | 最多 4 場 | E1：A8/B2；只依容量失敗或資源等待 >30% 決定 E2 採 B3 或 B2 | 可執行規則及設備條件；不依 Y 挑條件 |
| 凍結先導 | 4 場／2 組配對 | 同版本完整十日，記錄實際用量、耗時與資料完整性 | 規則、提示、記憶、模型及分析版本固定，預算足夠 |
| 正式比較 | 24 場／12 組新配對 | 相同初始設定、獨立世界與記憶；A/B 隨機順序、近時間交錯 | 保存全部嘗試及零結果，按協定處理失敗 |
| 分析 | 12 組為 n | 平均 B−A 百分點、配對 bootstrap 10,000 次、95% 區間；並列門檻敏感度 | 對所有原始配對及缺漏透明報告 |

## 模型接入時的工作清單

1. 讓 `propose` 的替代實作只接收角色自己的 observation，不把全場事件資料庫交給模型。
2. 回傳只允許一個動作，驗證固定 schema，再交給既有引擎。API key 留在伺服器端。
3. 以實際 tokenizer 管理 900 tokens 左右記憶預算，補上原始／轉述／反思區分及來源驗證。
4. 補上每天每人一次、最多三項來源可追溯反思，以及提示最多兩項相關反思。
5. 服務中斷暫停時鐘，只重試失敗者；格式錯誤最多修復兩次後 fallback wait；違反世界規則不重問。
6. 保存完整請求、回應、模型識別、usage、費用與時間，敏感憑證不寫入資料。
7. 加入檢查點恢復、正式設定／資料的密碼學雜湊、版本封存、人工編碼抽樣與配對分析。

正式開始前需完成全部啟動條件。十二組配對是固定資源下的估計型設計，不承諾特定檢定力或精度。
